  Two of those four are not work at all — they're a cold Cloud Run job and two
  chained 5 s poll loops. That's where "instant" actually comes from.

  A. Waits that aren't work

  1. Make the deploy runner resident instead of shrinking its image. The 104 s
  handoff is a Cloud Run job cold-starting to run our own pipeline.
  2026-08-06-deploy-cold-start.md attacks it with a smaller image + precompiled
  entrypoint (~30 s). The stronger move: a warm worker pool — 2–3 always-on
  containers pulling from a deploy queue. Dispatch cost goes to ~0 s, not 30.
  The job stays as the overflow path.

  2. Long-poll the desired state instead of a 10 s tick. main.go:562 is a fixed
  10 s sleep, so a placement waits ~5 s on average just to be seen. A Fetch()
  that passes wait=30s and a control plane that holds the response until the
  placement changes keeps the pull-only trust model intact (desired.go:3-13 —
  the node asks, nothing pushes) and makes delivery ~0 s. Same for the report
  direction.

  3. Choose the node before the build, not after. placeOnFleet calls chooseNode
  after buildImage returns (deploy-pipeline.ts:3546, fleet-place.ts:488), so
  nothing can be warmed while the build runs. Pick the node first and you unlock
  everything in section B.

  4. Overlap the serial prologue. Secrets are fetched after the build
  (allAppSecrets, right after buildImage), siblings build in a for loop one at a
  time, and inside the node's Start() the image pull, secret resolution and DB
  reachability check are strictly sequential (container.go:647) despite
  depending on nothing in each other. None of that is physics.

  5. Verify once, not twice. The redeploy path runs fleetProbe and then
  awaitRunning again (fleet-place.ts:570) — two chained 5 s-granularity loops.
  a45497e fixed the report lag; the doubled loop is still there, and the probe
  interval could mirror the router's own 500 ms file-watch cadence.

  B. Make the work smaller and overlapping

  6. Stop shipping the image twice. Cloud Build builds it, pushes hundreds of MB
  to Artifact Registry, and the node pulls the same bytes back — and per §3 of
  the research, that's a genuinely fresh digest every deploy, never a cache hit.
  Building on a fleet builder node in the same zone (or on the target node
  itself) means the image is already in containerd's store. The trust argument
  is already settled: we run untrusted code under gVisor on those machines:
  building under the same sandbox isn't a new boundary.

  7. Lazy pull — start the sandbox before the image finishes downloading.
  eStargz/SOCI + the stargz snapshotter turns pull time from O(image size) into
  O(what the first request touches). This is the highest-leverage unknown in the
  path, and it's the one thing that makes a fat Node image behave like a thin
  one without asking users to slim anything.

  8. Prefetch the digest. Even without lazy pull: the moment the build starts
  pushing, tell the chosen node to pull. It overlaps with verification, secret
  resolution and provisioning for free. Needs #3.

  9. Cheap pull wins: zstd layer compression on buildx (--output 
  type=image,compression=zstd) — meaningfully faster decompress than gzip for
  one flag; and distroless/prod-only-deps bases, since pull time is linear in
  bytes.

  10. Provision the database in parallel with the build. A first deploy with
  Postgres pays Cloud SQL creation and the build. They're independent.

  C. Spend the time before the user asks — the only route to actually instant

  For a changed repo, building takes real time. The trick is to have already
  done it.

  11. Content-addressed artifact cache. plan-cache.ts caches the decision keyed
  on the tree; extend the same idea to the artifact. If an image for this exact
  tree hash exists and the spec is unchanged, skip build and flip the placement
  — deploy becomes seconds, including for a fork of someone else's repo.

  12. Speculative builds. This is an agent-native product — the deploy agent is
  already sitting in the repo iterating. Build on save/commit, not on deploy.
  Likewise supersonic dev warming the build in the background. By the time the
  user types the command, the artifact exists and #11 hits. The design doc
  rejects a GitHub App for prebuilds because the dominant path is folder
  deploys, which is exactly why the local watcher is the better version of that
  idea.

  13. CLI dependency prebuild — already plan #2 in the design. Composes with #6
  and #7 rather than competing.

  D. Make the remaining seconds invisible

  14. Hold the first request instead of 503-ing. router.go:359 serves a 503 page
  when the route isn't healthy yet. If instead the router holds the connection
  (bounded, ~30 s) when a placement exists and the process is starting, then the
  deploy can be declared done the moment the route is written. The user's URL
  works immediately; the first hit absorbs the boot. This is what Koyeb and Fly
  do, and it converts real seconds into invisible ones — which is what "instant"
  means to the person watching.

  15. Return the URL at accept time, streaming logs after it, rather than at
  verify time.

  What I'd do first

  The honest gate is the one the repo already set for itself: 4afedde just
  landed fleet-pull / fleet-boot into deploy_stages, and nobody has read the
  numbers yet. Those two decide whether the money is in #6/#7/#9
  (pull-dominated) or #14 plus boot work (boot-dominated).

  Independent of that measurement, three things are free wins today: the warm
  deploy worker (#1), long-poll desired state (#2), and choose-the-node-first
  (#3) — together they take roughly 100 s of pure sequencing off every deploy
  without touching a single byte of build or pull.

  Platform overhead — everything that isn't the user's compile or the user's
  process booting — lands at roughly 2–3 seconds, down from ~200.

  What that means per shape

  Redeploy, nothing changed — artifact cache hit, placement already correct: ~1 
  s. It's a hash comparison and a no-op.

  Redeploy, source changed, deps unchanged — the everyday case: 5–15 s,
  essentially all of it the user's own vite build / tsc. A plain Node or Python
  server with no build step: ~3 s. With the CLI prebuilding, the compile leaves
  the wait and it's 3–5 s for everyone.

  First deploy, server-side build: 20–45 s, dominated entirely by dependency
  install. With the CLI dependency prebuild, 8–15 s — and now the upload of
  node_modules is the biggest single term, not anything we run.

  First deploy with a database: +1–2 s. Worth stating plainly because it looks
  like it should be the wall and isn't — you're on a shared instance
  (supersonic-shared-pg, pg-config.ts:10) with per-app roles, so provisioning is
  CREATE ROLE / CREATE DATABASE, not instance creation. Most competitors pay
  minutes here.

  Perceived, with request-hold: the command returns when the route is written,
  so subtract the boot and verify tail from every number above. A redeploy would
  print a working URL in ~1–2 s and absorb the boot on the first hit.

  Two things that can blow this up

  The cold planner. 87 s, and the cache only helps a repo shape someone has
  deployed before. A genuinely new shape pays it in full — which would make a
  first deploy 110 s, not 30. Every estimate above assumes a plan cache hit or a
  deterministic plan derived from repo facts. That's the largest single unfixed
  item and it isn't in the current decomposition.

  Pull and boot, if #6/#7 don't happen. Every "~0 s" in the push/pull row is a
  claim about work not yet done, sitting on a number nobody has read yet.
  fleet-pull / fleet-boot have been landing rows since 4afedde. If pull turns
  out to be 40 s against a cold registry, the redeploy floor is 45 s, not 5.

  The honest summary

  Sub-second is not reachable — dependency install and process boot are real.
  But 1 second for an unchanged redeploy, ~5 seconds for a changed one, and ~10 
  seconds for a first deploy is reachable, and at that point Supersonic isn't
  waiting on itself at all: every remaining second belongs to the user's own
  code. That's a number no competitor publishes, which per
  market-first-deploy.md is itself the differentiator.
