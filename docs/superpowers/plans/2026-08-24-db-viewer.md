# The database viewer: from a grid to something you can work in

Written 24 Aug 2026. Supersedes nothing; extends
`docs/superpowers/specs/2026-08-20-database-view-design.md`, whose rule still
holds and is the reason several things below are refusals rather than features:
**a number we cannot vouch for is labelled, and a fact the database cannot supply
is omitted.**

## Where it is now

`components/DatabasePanel.tsx` and `app/api/apps/[slug]/db/route.ts`.

Working: a list of tables with row counts, column counts and last-write times; a
per-table grid in mono with type-aware alignment, a sticky header, a row-ordinal
gutter and `null` as its own token; one `SELECT` box; ordering chosen server-side
and *reported* rather than assumed; `~` on estimated counts.

The API takes exactly three parameters — `table`, `limit`, `offset`. That is the
constraint behind most of what follows.

## What Supabase has that we do not, and which of it we want

Measured against our job — "did my data land" — not against being a database IDE.

| | Why it matters here |
|---|---|
| A table list that stays | Five tables and you cannot move between them without going back. The biggest single reason it does not feel like a database. |
| Cell expansion | We truncate at 22rem with a `title`. `orders.shipping` is jsonb and `products.tags` is an array — exactly the values somebody opens this screen to read. |
| Sort by column | "Did it land" is usually answered by sorting on a timestamp or an id. |
| One filter | The commonest question is "is MY row there". Today the only way to ask is SQL. |
| Refresh | The point is watching data arrive; we only re-read on mount. |
| A real SQL surface | One line, one statement, results in a cramped table, no history. |
| Single-row editing | See the security note — this is the one that changes the threat model. |

Deliberately NOT copied: bulk edits, saved queries, the ERD, schema migrations.
Those make a database IDE, which is a different product.

Two things already paid for and thrown away:

- **The primary key is known server-side** (`TableShape.primaryKey` in
  `lib/db-browse.ts`) and is not in the `Page` payload. Marking the PK column and
  freezing it during horizontal scroll are free once it ships.
- **Indexes and defaults** are in `information_schema` and never read. A schema
  tab costs one more query.

## The order, and why it is this order

Each phase is shippable on its own and none blocks the next.

### 1 — The list stays (half a day, no API change)

Two panes: tables on the left at ~200px, the open table on the right. The list
keeps its counts and its last-write times, so it is the summary screen AND the
switcher.

`?table=` in the URL, using `useQueryState` — the workbench already puts `tab`,
`view` and `addr` there, so a link to one table is free and a reload keeps it.

**Done when** clicking three tables in a row makes three requests and no
navigations, and a reload lands on the same table.

### 2 — A cell you can open (half a day, no API change)

Click a cell → a panel with the whole value: jsonb pretty-printed, arrays one per
line, long text wrapped, and a copy button. `Esc` closes it.

The row's other columns come with it, because the reason to open a cell is usually
to identify the row it is in.

**Done when** a 4KB jsonb value is readable and copyable, and no cell needs a
tooltip to be understood.

### 3 — Sort and filter (1 day, API change)

`?sort=<column>&dir=asc|desc` and `?where=<column>&op=eq|neq|gt|lt|contains&value=…`.

Both validated against the table's real columns — `isSafeIdent` plus membership
in `TableShape.columns`, never string interpolation of a caller's text into SQL.
The operator is an allow-list, the value is a bind parameter. The existing
`STATEMENT_TIMEOUT_MS` covers the "somebody filtered a big table" case.

The reported ordering line stays and now names the person's choice instead of the
default, which is what keeps the screen and the SQL from disagreeing.

**Done when** a filter on a text column and a sort on a timestamp both work, and a
crafted `sort=x;drop table y` is refused by the identifier check rather than by
Postgres.

### 4 — Refresh, and the PK (half a day)

A refresh button on the grid and on the table list. `Page` gains `primaryKey:
string[]`; the PK column is marked in the header and sticky on the left.

**Done when** watching a seed run means pressing one button, and scrolling a wide
table sideways keeps the key visible.

### 5 — The SQL surface (1 day)

A textarea, ⌘↵ to run, results in the same grid component as a table, the
statement in the URL so it is shareable, and the last few statements kept in
`localStorage` — not on the server, because a query is not something we should
retain on somebody's behalf.

Server-side rules unchanged: one statement, `SELECT` only, bounded timeout. They
are the security boundary and they stay where they are.

**Done when** the SQL box is the thing you reach for instead of a workaround for
missing filters.

### 6 — Single-row editing (1–2 days, and the one to think about)

**This changes the threat model, so it is last and it is narrow.**

The chat agent's `/db` tool stays read-only. That property is the only thing
bounding a prompt injected through an app's own rows — see the workbench spec —
and it is not negotiable for a UI convenience.

So editing is a HUMAN path and looks nothing like the agent's:

- A separate route (`PATCH /api/apps/[slug]/db/row`), session cookie and owner
  only, never a bearer token.
- One row, identified by its full primary key, with the old value sent back for a
  compare-and-set so two tabs cannot silently overwrite each other.
- **No editing on a table with no primary key.** If we cannot name the row, we
  cannot promise to change only that one.
- No editing of generated or identity columns.
- Every write logged with the user id, the table, the key and the column.

**Done when** fixing one wrong row takes a click, and the agent still has no
verb that writes.

## The thing that is not UI

**Per-app backups do not exist.** `lib/backups.ts` has `BACKUP_BUCKET`,
`backupObject` and `exportArgs`, and **zero callers** — verified 24 Aug. Cloud SQL
automated backups on `supersonic-shared-pg` are on (daily 08:00 UTC, 14 retained,
PITR with 7 days of logs, last three SUCCESSFUL), but that is the whole shared
instance: restoring it restores every tenant together, so there is no way to give
one person their app back.

The Pro plan lists "Backups and restore". Until `exportArgs` is called on a
schedule and there is a route to restore one database, that line is a promise we
do not keep — which matters more than any item above, because it is the only one
where somebody can lose something.
