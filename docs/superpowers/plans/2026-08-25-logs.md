# Logs: six streams, one store, two screens

Written 25 Aug 2026. Replaces the Infra screen.

## Where this got to

**Built and in production: 1, 3, 4, 5, 7.** The reader, the edge publisher and
the fleet agent's platform events, the Runtime screen with its live tail, the
deploy transcript, and the agent and CLI. Verified against a live app on 25 Aug:
four requests made against `z1b3k.thebay.cloud` appeared as `GET /cart 200 19ms`
with `face` null, through the deployed proxy.

**Not built: 2 and 6.**

- **2 — the retention bucket.** Everything still ages out at 30 days on
  `_Default`, so "all the logs" is not true yet. Nothing is lost that would not
  have been lost anyway; it is the promise that is outstanding.
- **6 — browser logs.** Nothing collects them, so the `Frontend` segment holds
  only what a test published by hand. This is the one with the security surface:
  an unauthenticated public ingest endpoint, needing a rate limit and a payload
  cap before it exists rather than after.

One thing phase 3 could not verify: the platform events fire on a crash, a
restart or a give-up, and no app obliged during the deploy. The code is live and
the path is tested; it has not been *seen* in production.

Everything below rests on numbers measured against production on 25 Aug, not on
estimates. They are quoted where they decide something.

## What is true today

`Infra` shows two things: "No errors" and "Nothing scheduled". Neither is a log.
The screen that should answer *what is my app doing* answers nothing, while five
of the six streams that could answer it already exist.

**The pipe works.** Fleet nodes run the Google Cloud Ops Agent with a glob —
`/srv/apps/*/*.log`, `record_log_file_path: true` — so every app's stdout reaches
Cloud Logging labelled with its file path, no per-app registration. `lib/log-filter.ts`
already unions the two runtimes: `cloud_run_revision` by service name OR
`gce_instance` anchored on `^/srv/apps/<slug>/`. That anchor exists because a
substring match for `subio` also returned `/srv/apps/subio-2/app.log` — one
tenant's lines in another's query. It stays.

**Three facts that shape the design:**

1. **There is no backfill, ever.** `l3sgp` has been running since 14 Aug and has
   zero lines at seven days. It prints nothing, and a file tail has no history —
   whatever it said at startup was written before the agent held a position in
   that file. The empty state must therefore say *"nothing since 09:14"* and never
   *"no logs"*. Those are different facts and only one of them is ours to fix.

2. **The 1-hour default window is why the screen looks empty.** `z1b3k`: 0 lines
   at 1h, 12 at 24h. A quiet app currently reads as an app with no logs.

3. **Node-shipped lines all arrive as severity `DEFAULT`.** The ops agent does not
   parse levels out of raw stdout. So "errors only" cannot work on app stdout
   until something structures it, and the UI must not offer a filter that
   silently matches nothing. Cloud Run apps do get real severities.

## The six streams

| | Where it is now | Work |
|---|---|---|
| App stdout/stderr | Cloud Logging, both runtimes | none — it is there |
| Build log | Cloud Build, via `lastBuildLog` | surface it as a source, not a fallback |
| Deploy narration | `deploy_events` in Postgres | publish to the store |
| **Edge requests** | **discarded** | publish — see below |
| **Platform lifecycle** | **invisible** | publish |
| Browser | does not exist | build (phase 6) |

Two of those are the find. **The edge stands on the path of every request to
every hosted app and keeps aggregates only, in memory.** `services/proxy/src/xray.ts`
says so itself: *"There is no table, no retention story and no history: this
answers what is happening, not what happened."* Sixty paths per app, sixty
duration samples, three hundred apps, all lost on restart. One line per request —
method, path, status, ms — is the stream Vercel's log view is built on, and we
compute it and throw it away.

And **the fleet agent knows when it placed an app, restarted it after a crash,
failed a health check, moved it between nodes or rolled it back**, and tells
nobody. That is the stream that answers "why did my app restart at 3am", which is
currently unanswerable by any means.

Deliberately **not** streams: certificate and DNS events, which belong in Address
where you act on them; and the chat agent's own tool calls, which are an audit
trail and not the app's behaviour.

Later, not now: per-process worker logs (already caught by the ops agent glob, so
they arrive on their own and want a *filter*, not a stream), cron invocations, and
Cloud SQL logs for slow queries and deadlocks.

## Retention: all of it, for everybody

Measured on the two busiest fleet apps: **1,073 and 1,071 entries/hour**, ~730 B
per entry as JSON. That is **0.3–0.6 GiB per app per month.**

Cloud Logging charges ~$0.50/GiB **ingested** with the first 50 GiB per project
per month free, and ~$0.01/GiB/month for retention **beyond** 30 days. The maximum
retention is 3650 days.

| Scale | Ingest | Ingest cost | Keeping everything |
|---|---|---|---|
| today, ~20 apps | ~9 GiB/mo | free | ~$1/mo in year 1 |
| 110 apps | ~50 GiB/mo | free (at the cap) | ~$6/mo |
| 1,000 apps | ~450 GiB/mo | ~$200/mo | ~$55/mo, +$55 each year |

**So retention is nearly free and ingest is the whole cost — and ingest is paid
identically whether a line is kept for an hour or a decade.** A retention window
saves almost nothing. There is no plan gating, no window picker, no "upgrade to
see older logs".

What that does mean: **the cap has to be on RATE, not on age.** One app logging
100 lines/second is 260 GiB/month by itself — $105/month from a single tenant, and
no time window prevents it. Per-app ingest ceiling, with dropping made visible
("1,204 lines dropped"), because silent sampling is what makes people stop
trusting a log view.

The one exception is **browser logs**, which stay at 30 days on every plan. They
carry end-user data — emails in stack traces, tokens in URLs, form values — and
holding a decade of somebody else's users' error text is a compliance decision
that does not get better for being cheap.

## Two screens, and why not frontend/backend

The obvious split is Frontend and Backend. It is the wrong cut, for three reasons.

**It does not simplify.** Of the six streams exactly one is frontend. The other
five are backend, so one tab is thin and the other still needs every filter the
split was meant to avoid.

**A build wants a different UI, not a different filter.** A build is bounded: you
read it top to bottom once and jump to the step that failed. That is a transcript.
Runtime is infinite: you tail it, search it, facet it. That is a table. Those are
two screens. Frontend versus backend is the same screen twice.

**Edge requests do not classify.** `GET /dashboard → 404` is frontend routing;
`POST /api/users → 500` is backend. The edge sees both and cannot reliably tell
them apart, so forcing a choice puts the line you are hunting in the tab you did
not open.

And the thing tabs would cost: a 500 from an API and the browser error it caused
belong **on one screen, seconds apart**. That is the debugging moment, and a
frontend/backend split makes it impossible.

So:

- **Runtime** — live tail, search, and a segmented control across the top:
  `All · Frontend · Backend · Requests`, defaulting to All, with the finer facets
  behind it. One click for the two-way division; nothing hidden.
- **Deploys** — the build transcript for a deploy with our pipeline's narration
  interleaved, opening at the failure.

Jobs leaves this screen for a section of its own, with its own UI.

## The field contract

Everything hangs off this, so it comes before any code. Published entries carry
a `jsonPayload`:

    slug      the app
    source    app | edge | browser | build | deploy | platform
    face      frontend | backend        — ABSENT on edge, deliberately
    level     debug | info | warn | error   (and a real Cloud Logging severity)
    msg       the line
    process   web, or a worker's name
    release   image digest or version, so a line can be tied to what was running

    # source=edge
    method path status ms bytes ua

    # source=browser
    url line col stack session

**`face` is stored, not computed.** Cloud Logging filters cannot express a CASE,
so whoever writes the entry decides, once. And `face` is **omitted** on edge
requests rather than guessed — that is the honest consequence of them not
classifying, and it is why `Requests` is its own segment rather than being folded
into one side.

`severity` is set properly on everything we publish, which is what makes an
"errors only" filter work on those streams even though app stdout arrives as
`DEFAULT`.

## Reading: one query path

The existing code shells out to `gcloud logging read` per request, which measured
**2–4 seconds** — process spawn and auth, not the API. A live tail cannot be a
subprocess.

So `@google-cloud/logging` is added, and it is the first Google client library in
this codebase — everything else spawns `gcloud`. Justified by two things a
subprocess cannot do: `tailLogEntries`, which is a real server-side stream, and
page tokens, which are stable cursors.

That gives all three of the hard requirements at once:

- **Pagination** — Cloud Logging page tokens. Stable under new writes; no offset
  drift, which is the thing that makes a log list skip and repeat lines.
- **Search that does not cost us anything** — the filter is evaluated by Google's
  index. We forward a string and stream rows. Our server holds no log data, has
  no log table to scan, and cannot be made slow by somebody's regex.
- **Facets** — the fields above, as indexed equality tests.

One caveat to design around now: `tailLogEntries` has a per-project concurrent
session limit. One upstream tail per APP, fanned out to that app's viewers over
SSE — never one tail per browser.

## Phases

Each ships alone and none blocks the next.

### 1 — `lib/logs.ts`: the filter, the reader, the shape (1–2 days)

The filter builder, the paginated read, the normaliser that turns four different
entry shapes into one row type. `appLogFilter`'s union survives inside it. The
existing `/api/apps/[slug]/logs` route moves onto it and keeps answering the same
way, so the CLI and the agent are unaffected.

**Done when** the current logs route returns the same lines through the new
reader, and a page token walks backwards without repeating a line.

### 2 — The bucket and the sink (half a day, infrastructure)

A dedicated log bucket for tenant app logs at 3650 days, and a sink routing the
app sources into it. `_Default` stays at **30 days**.

Not just raising `_Default`: it holds the control plane's own logs too, and we
would be paying to keep our noise for a decade. A separate bucket also puts
tenant data somewhere we can point at when somebody asks where their logs live.

**Done when** a line written today is readable at a 31-day-old timestamp offset,
and platform logs still age out at 30.

### 3 — Publish what we already throw away (2 days)

Edge requests from the proxy, one entry per request, with the fields above. The
in-memory aggregate stays — it answers "right now" and is what the panel reads —
but it stops being the only record.

Platform lifecycle from the fleet agent: placed, started, health check failed,
restarted, moved, rolled back.

Both behind the per-app rate cap from the start, not after the first incident.

**Done when** a request to a hosted app is a searchable line within seconds, and
killing a container produces a `platform` line saying so.

### 4 — The Runtime screen (2–3 days)

Live tail over SSE, one upstream tail per app. Search box. The segmented
`All · Frontend · Backend · Requests`. Facets for level, process, status, path.
Pagination backwards through history.

Empty state says *"nothing since HH:MM"* — never "no logs". A filter that cannot
match on a given source is disabled with the reason, not offered and silent.

**Done when** a person can watch a request arrive, see the 500 it produced, and
scroll back a week without the page stalling.

### 5 — The Deploys screen (1–2 days)

Build transcript per deploy, our narration interleaved, opening at the failing
step. This is `lastBuildLog` and `deploy_events` promoted from fallbacks to a
screen of their own.

**Done when** "why did my deploy fail" is answered by the first thing on screen.

### 6 — Browser logs (2–3 days, and the one with a security surface)

A collector in the script the proxy already injects into every HTML page —
`window.onerror`, `unhandledrejection`, `console.error`, failed fetches — posting
to an ingest endpoint that writes into the same store with `source: browser`.

**This is an unauthenticated public endpoint and must be designed as one.**
Anyone can POST to it; `Origin` is trivially forged outside a browser. So: a
per-app rate limit and a payload cap enforced before anything is written, sampling
above a threshold, and a hard length cut on every field. The endpoint must be
incapable of costing us more than a fixed amount per app per hour, whatever is
sent to it.

30-day retention, and said in the product.

**Done when** an exception in a hosted app's page appears beside the request that
served it, and hammering the endpoint from curl cannot raise our bill.

### 7 — The agent and the CLI (1 day)

`./logs` gains the same filter grammar, so the agent can ask for one source, one
level or one path instead of reading everything. `bay logs [--follow] [--source]`
streams through the same reader.

Nearly free, because both are thin callers of phase 1 — which is the point of one
store and one query path, and the reason not to build three log views.

## What this does not do

No log store of our own. No Postgres table of lines, no retention job, no
compaction, no index we maintain. Cloud Logging is the store, it is already where
both runtimes write, and its search is the feature we would otherwise be building
badly.

No metrics. Counting requests per minute over a log stream is the wrong tool; if
that is wanted it is a separate surface reading the aggregates the edge already
keeps.
